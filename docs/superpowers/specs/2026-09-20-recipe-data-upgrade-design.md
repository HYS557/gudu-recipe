# 咕嘟食谱全量数据升级设计

## 1. 目标

先一次性升级现有 961 道食谱的数据结构、营养口径、时间口径、份量换算、食材替换和保存复热信息；全量升级通过验收并发布后，再新增酱料、高汤与汤底、腌料、馅料、卤水与底料、干料与撒料、腌菜与泡菜、厨房基础制作、预制与备餐分类。

升级必须保留现有食谱 ID、收藏数据、搜索入口和自动更新机制，安卓与苹果端使用同一套数据。

## 2. 明确不在范围内

- 不修改或新增火候与熟度标准。
- 不新增失败补救模块。
- 不处理来源在用户界面的展示。
- 暂不处理图片授权、图片来源和外链图片问题。
- 不在 961 道升级完成前新增上述内容分类。

## 3. 实施顺序

### 阶段一：升级现有 961 道食谱

1. 建立统一字段规范和计算规则。
2. 将现有基础数据及历次修正合成为规范化食谱数据。
3. 为 961 道食谱补齐新字段。
4. 升级详情页展示与份量切换。
5. 执行全量数据审计、自动化测试和手机端抽样验证。
6. 通过增量更新机制发布新数据版本。

### 阶段二：新增内容分类

阶段一全部通过后，依次增加：

1. 酱料与蘸料
2. 高汤与汤底
3. 腌料
4. 馅料
5. 卤水与底料
6. 干料与撒料
7. 腌菜与泡菜
8. 厨房基础制作
9. 预制与备餐

新增内容沿用阶段一确立的全部字段和验收规则，不另设较低标准。

## 4. 统一数据模型

每道食谱保留当前字段，并新增以下结构化字段。字段名称在实施计划中可依据现有代码风格调整，但含义不得改变。

### 4.1 营养与成品重量

```js
nutrition: {
  finishedWeightG: 0,
  servingWeightG: 0,
  servings: 0,
  total: {
    caloriesKcal: 0,
    proteinG: 0,
    fatG: 0,
    carbsG: 0
  },
  perServing: {
    caloriesKcal: 0,
    proteinG: 0,
    fatG: 0,
    carbsG: 0
  },
  per100g: {
    caloriesKcal: 0,
    proteinG: 0,
    fatG: 0,
    carbsG: 0
  },
  assumptions: []
}
```

规则：

- `finishedWeightG` 表示烹饪完成后的可食用成品估算重量，不使用生料总重代替。
- `servingWeightG = finishedWeightG / servings`，允许因四舍五入产生不超过 1 克的差异。
- 总量、每份和每 100 克三套数据必须能够相互反算，热量允许不超过 2% 的舍入差异，三大营养素允许不超过 0.2 克的舍入差异。
- 炸制菜的营养估算记录吸油假设；汤、火锅和带大量汤汁菜记录是否按饮用全部汤汁计算。
- 展示时明确“估算值”，不作为医疗、疾病治疗或精确减重依据。
- 继续兼容当前 `calories` 和 `caloriePerServing` 字段，由规范化数据生成兼容值，避免旧页面或旧更新包失效。

### 4.2 时间拆分

```js
timeBreakdown: {
  activeMinutes: 0,
  prepMinutes: 0,
  cookMinutes: 0,
  soakMinutes: 0,
  marinateMinutes: 0,
  fermentMinutes: 0,
  restMinutes: 0,
  coolMinutes: 0,
  totalElapsedMinutes: 0,
  applianceVariants: []
}
```

规则：

- `activeMinutes` 是需要持续人工操作的时间，不能与其他时间简单重复累计。
- `totalElapsedMinutes` 以真实经过时间计算；可并行步骤不得重复相加。
- 不适用的项目使用 0，不使用空字符串或含糊文字。
- 粥类至少提供普通锅、电饭煲和压力锅中适用的方式；不适用的设备不强行填写。
- 保留现有 `prepTimeMinutes`、`cookTimeMinutes` 和步骤计时器，兼容值由新结构生成或校验。

### 4.3 份量换算

```js
scaling: {
  baseServings: 0,
  supportedServings: [1, 2, 4, 6],
  ingredientRules: {},
  seasoningRules: {}
}
```

换算规则分为三类：

- 线性：肉类、蔬菜、主食、水果等主体食材按人数同比例换算。
- 缓增：盐、酱油、糖、醋、辣椒、香辛料等使用分段系数，人数增加时低于线性增长。
- 工艺约束：炸油、焯水、煮面水、卤水、勾芡液等按锅具和覆盖需求计算，不作为最终全部摄入量同比例放大。

页面固定提供 1、2、4、6 人份选择，并始终显示“先少量调味，出锅前尝味调整”的提示。切换人数只改变显示值，不修改原始基础配方。

### 4.4 食材替换和饮食调整

```js
alternatives: {
  ingredientSwaps: [],
  dietaryVariants: {
    lessOil: null,
    lowSodium: null,
    mild: null,
    vegetarian: null
  }
}
```

规则：

- 只填写在该食谱中实际可行的替换，不为追求字段完整而编造替代方案。
- 每项替换注明替换比例、对味道或质地的影响，以及是否改变烹饪时间。
- 少油、低盐、不辣和素食版本按适用性提供；不适用时为 `null`，页面不展示。
- 替换方案涉及现有结构化过敏原时，必须同步更新替换后的过敏原提示。

### 4.5 保存与复热

```js
storage: {
  roomTemperatureMinutes: null,
  refrigeratedDays: null,
  frozenDays: null,
  freezeRecommended: false,
  overnightRecommended: false,
  reheatingMethods: [],
  notes: []
}
```

规则：

- 时间从食物完成烹饪或完成冷却后的合理节点计算，文字中明确前提。
- 不建议常温存放、冷冻或隔夜的食物直接标记为不建议，不填写误导性的期限。
- 复热方法包含设备、时间范围和必要的加水、覆盖或翻动说明，但不新增本项目已排除的熟度标准模块。
- 凉菜、生食、米饭、海鲜、乳制品和含蛋酱料使用更保守的保存说明。

## 5. 数据生成与校验

### 5.1 规范化数据源

现有 `recipes.js`、食谱内容修正、元数据修正、过敏原修正和营养修正先按当前加载顺序合并。合并结果作为规范化数据的输入，不能丢弃后加载修正对前序数据的覆盖。

生成流程必须可重复运行，并保证相同输入产生相同输出。生成工具只负责机械合并、公式计算和格式验证；需要判断菜品成品重量、吸油、保存方式或替换可行性的内容，必须在结构化数据中明确记录，不能由页面运行时随机推断。

### 5.2 营养计算

- 以结构化食材重量和可食部为基础计算。
- 对“适量、少许、若干”等无法计算的用量先补为合理的克数范围或设定明确计算假设。
- 油炸、带骨食材、干货泡发、吸水主食和大量汤汁菜分别使用对应的重量修正规则。
- 配方中未实际摄入的焯水、煮面水和剩余炸油不得全部计入热量。
- 每一道食谱保留营养估算假设，方便以后重新计算。

### 5.3 全量审计

961 道食谱必须全部满足：

- ID 唯一且与升级前一致。
- 必需字段存在、类型正确、数值非负。
- 总营养、每份营养和每 100 克营养反算一致。
- 成品重量、份数和每份重量一致。
- 总耗时不小于任何不可并行的单项时间。
- 1、2、4、6 人份换算不产生 0 克、负数、`NaN` 或明显异常调味量。
- 保存与复热字段符合格式，不展示空模块。
- 现有来源复核状态、过敏原和收藏 ID 不丢失。

## 6. 数据文件与更新机制

- 将大量按版本堆叠的修正脚本收敛为一个规范化食谱数据文件和少量必要的版本元数据。
- 构建阶段生成浏览器和 APK 可直接加载的数据资源。
- 自动更新包继续以食谱 ID 为键进行增量覆盖，兼容现有 `patches`、`upserts` 和 `removeIds`。
- 数据版本单独递增，不因仅更新应用界面而强制重复下载全部食谱。
- 首次迁移时保留旧数据加载回退路径；新数据和页面通过验收后再移除冗余修正脚本引用。

## 7. 页面设计

详情页保持现有核心步骤优先，新增信息采用折叠区，避免首屏过长：

1. 营养与份量
2. 时间明细
3. 食材替换与饮食调整
4. 保存与复热

份量选择位于食材列表附近。切换 1、2、4、6 人份时，即时更新食材和调味料用量；营养信息同步显示对应总量和每份值，每 100 克值保持不变。

旧版食谱数据缺少新字段时，页面必须安全隐藏对应模块，不能显示 `undefined`、0 天保存或错误换算。

## 8. 兼容性与数据迁移

- 食谱 ID 不变，现有收藏和历史记录继续可用。
- 旧版 APK 无法理解的新字段由兼容字段兜底；已安装自动更新版可获取新的数据包。
- 苹果主屏幕版通过服务工作线程版本更新获取新界面和数据。
- 数据迁移失败时保留应用内置食谱，不让应用因远端更新包损坏而无法打开。
- 更新包继续执行 SHA-256 校验，校验失败不写入本地缓存。

## 9. 验收与发布

### 自动化验收

- 961/961 道通过数据模式校验。
- 961/961 道通过营养一致性校验。
- 961/961 道通过时间字段校验。
- 961/961 道通过份量换算四档测试。
- 页面脚本语法检查通过，无控制台致命错误。
- 更新包哈希与清单一致。

### 人工抽样

按炒、炖、炸、蒸、汤、粥、面点、凉菜、饮品和复杂宴席菜分层抽样，检查至少 30 道；粥类和油炸类必须纳入抽样。

### 设备验收

- 桌面浏览器检查首页、搜索、详情页和份量切换。
- 已连接安卓手机检查数据更新、详情展示、份量切换及收藏保留。
- 苹果网页版本检查服务工作线程更新后的显示。

### 发布门槛

只有全部自动化验收通过且设备抽样无阻断问题，才能发布 961 道升级数据并进入阶段二。阶段二新增分类不得与阶段一并行发布。

## 10. 完成定义

“现有食谱升级完成”必须同时满足：

- 961 道食谱全部补齐适用的新字段并通过全量审计。
- 手机端能够正确展示新模块并完成四档份量切换。
- 自动更新包已发布并在已连接安卓机验证。
- 原有收藏、搜索、分类和食谱步骤不受影响。
- 不包含已明确排除的火候熟度、失败补救、来源展示及图片授权工作。

达成以上条件后，自动开始阶段二的新分类内容建设。
